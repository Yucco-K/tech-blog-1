## はじめに

Gmail の未読が、気づけば 1000 件を超えていました。

必要なメールが埋もれていないか気になるのに、一件ずつ確認するのは大変で、受信トレイを開くだけで少し気が重くなる。そんな状態をなんとかしたいと思っていました。

Google カレンダーも、予定を登録するためだけに使っていました。その日の予定が重なっていないか、空き時間がどこにあるかは毎回自分で確認する必要があり、いまひとつ使い勝手がしっくりきていませんでした。

メンティーとしての活動でも、同じような繰り返しがありました。月に一度メンターへ取り組みを報告する準備として、コラボレーターとして参加している GitHub リポジトリで、自分が担当している Issue や Pull Request を開き、ステータスや概要を確認してはスプレッドシートへ手作業で転記します。毎回ほぼ同じ作業の繰り返しでした。

さらに、コストコの特売情報を確認するために、ほぼ毎日 YouTube を見ていました。「もっと短時間で、一番近い倉庫店に関係する食品のセールだけ確認できたら」と思いながら。

こうして並べてみると、身の回りには小さな繰り返し作業がいくつも転がっていました。そこで、Codex を使ってこれらを自動化してみることにしました。

## 最初に決めたのは「何をさせないか」

自動化というと、決まった時刻に処理を実行することを想像しがちです。しかし実際に取り組んでみると、スケジュールを組むだけでは全く足りませんでした。

何より大切だったのは、自動化する範囲と、絶対に自動化しない範囲を最初に線引きすることです。今回作った仕組みは、基本的に「情報を集めて整理し、私に報告するところまで」に限定しました。

- メールを勝手に送信しない
- カレンダーの予定を作成・変更・削除しない
- GitHub の Issue や Pull Request を書き換えない
- コストコの商品を購入したり、会員情報を操作したりしない

判断と最終的な操作は、必ず自分が行います。この「やらないことを決める」という発想が、安全に自動化を運用するための土台になりました。

## Gmail：未読を減らすより「判断しやすくする」

Gmail では、届いたメールを次の 3 種類に整理するようにしました。

- 返信が必要
- 返信以外の対応が必要
- 対応不要

目的は未読件数を減らすことではなく、「自分が何をすべきか」を短時間で判断できる状態にすることです。

返信が必要なメールには返信案も作らせますが、自動送信はしません。宛先・送信元やメールの内容を確認し、私が明確に承認したときだけ送信する運用にしました。セキュリティ通知のように、返信は不要でも確認や設定変更が必要なものは「返信以外の対応が必要」に分類します。

この仕組みにしてから、受信トレイを上から順に読む作業が、必要なものから優先して判断する作業に変わりました。

## Google カレンダー：予定表から「朝のブリーフ」へ

カレンダーでは、毎朝 8 時にその日の予定を確認し、時刻順にまとめるデイリーブリーフを作りました。予定の一覧に加えて、次の点も確認させています。

- 予定が重複していないか
- 休憩なしで連続していないか
- 移動時間を確保しにくい箇所がないか
- まとまった空き時間がどこにあるか

カレンダーを開いて一つずつ確認しなくても、その日の流れと注意点を朝のうちに把握できるようにするのが狙いです。

ただし、この自動化タスクでは、カレンダーを完全な読み取り専用と決めました。予定の作成・変更・削除、参加者への連絡は一切行わないことを実行方針に明記しています。

## メンタリング準備：GitHub とスプレッドシートをつなぐ

メンタリングの準備では、GitHub の Issue や Pull Request から対象期間の取り組みを確認します。これまでは各ページを開いてステータスや概要を読み、スプレッドシートへ手で転記していましたが、自動化後は新しく報告すべき内容を探し、現在の状況を整理するところまで任せられるようになりました。

ここで特に気をつけたのは、既存のスプレッドシートを勝手に整形しないことです。もとの文章、並び順、書式はそのまま維持し、本当に新しい情報だけを追加します。GitHub 側も検索・参照・要約に限定し、Issue や Pull Request そのものには手を加えません。

つまり、エージェントに報告書を完成させてもらうのではなく、私がメンターに説明するための材料を集めてもらうイメージです。

## コストコの情報：「安い」だけでなく条件まで確認する

コストコの特売情報では、食品を優先しつつ、価格・値引き額・対象期間・対象倉庫店を確認するようにしました。

難しかったのは、公開情報に近所の倉庫店が明記されていない場合です。そこで「近所の倉庫店を除外する記載がない」ことと「近所の倉庫店で確実に販売されている」ことを明確に区別しました。確実でない情報には「除外記載なし。店舗での確認が必要」と付記させています。まだまだ改善が必要な段階ですが、コツコツと改善しながら、自分が本当に欲しい情報をピンポイントで表示してもらえるように工夫していきたいと思います。

YouTube を全部見る代わりに、まず短い一覧を確認し、気になる商品があったときだけ詳しく調べる、という流れに変えていきたいです。

## 一番つまずいたのは処理ではなく「保存」と「通知」

自動化の処理そのものは動いても、実行ログを保存できないことがありました。設定は正常に行えているように見えていても、スケジュール実行時には読み取り専用の環境で動き、ログファイルへの追記が拒否されるケースがあったのです。

ここで学んだのは、「結果を作れたこと」と「結果を保存できたこと」は別々に確認しなければならない、ということでした。そこで次のように見直しました。

- 保存先を曖昧な指定ではなく絶対パスにする
- エージェントから書き込める場所を明示する
- エージェントが実行後にログファイルをもう一度読み、追記されたことを確認する
- 保存に失敗した場合は、結果とは分けて失敗を報告する
- カレンダーの結果はローカルのログと Google スプレッドシートの両方に記録する（人間の目で読み取りやすくするため）

「保存しました」と表示されていても、実際のファイルを確認するまでは完了と判断しない。そう運用を変えました。

通知でもかなり苦労しました。Mac には通知が表示されるのに、iPhone には届かないことがありました。iPhone 側の通知設定、ChatGPT アプリの設定、即時通知、Mac との接続、再ペアリングと、一つずつ確認して回りました。iPhone ミラーリングや画面共有中は、Mac 側の通知バナーやサウンドが抑制される場合があることも分かりました。

設定を変えるたびに一度限りのテストを送り、Mac と iPhone のどちらに届いたかを切り分けました。それでも Codex のプッシュ通知は安定しなかったため、最終的に Google カレンダーや他の自動化タスクの結果を自分宛ての Gmail でも送るようにしました。Gmail の通知を代替プッシュとして使う方法です。テストメールが実際に iPhone の Gmail へ届くことも確認できました。

## まとめ：自動化は、作って終わりではなかった

今回の挑戦で分かったのは、自動化は「毎朝 8 時に実行する」と設定すれば完成するものではない、ということです。安定して使うためには、少なくとも次の要素が必要でした。

- 何を実行するかを定めた実行方針
- 絶対に行わない操作を決めた安全ルール
- 実行されたことを確認するログ
- 結果を確実に受け取るための通知経路
- 本当に保存・送信されたかを確かめる検証

実際には、正常に動いた処理よりも、ログが残らなかったり通知が届かなかったりしたときのほうが、学びは多かったです。

自動化によってすべての作業がなくなったわけではありません。それでも、メール・カレンダー・GitHub・セール情報を毎回ゼロから探す作業は確実に減りました。私がすることも、「情報を探して転記する」ことから「整理された情報を確認して判断する」ことへ、少しずつ変わってきています。

これからも、作った自動化タスクを実際に使いながらブラッシュアップしていきたいと思います。通知の安定性を高めること、報告内容をさらに分かりやすくすること、失敗したときに自分で原因を切り分けられるようにすること。改善したいところはまだたくさんあります。

身近な繰り返し作業を一つずつ任せられるようにして、最終的には、自分の代わりに勝手に判断する存在ではなく、必要な情報を集め、整理し、安全に届けてくれる「自分専用の秘書」を作れるように。これからもチャレンジを続けていきたいです。
