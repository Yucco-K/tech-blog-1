## はじめに

教育系Webサービスで、スクールごとに教材を組み合わせて独自の学習経路を作成できる「カスタム学習ロードマップ機能」の開発を担当しました。

この機能では、管理画面でロードマップを作成し、教材を選択・並び替え・公開します。学習者向けページでは、ロードマップに沿った教材と学習進捗を確認できます。

単なる一覧画面の追加ではなく、CMS、学習者向けUI、API、データベース、公開状態、進捗表示、キャッシュ、既存の学習導線まで複数の領域にまたがる機能でした。

:::message
この記事では、守秘義務に配慮してプロジェクト名、内部URL、Issue・PR番号、具体的なモデル名や変数名を一般化しています。コードは実務コードそのものではなく、考え方を説明するためのサンプルです。
:::

## 1. なぜカスタムロードマップが必要だったのか

固定されたコース構成だけでは、スクールごとの学習方針に合わせて教材を組み替えることが難しいという課題がありました。

例えば、スクールによって次のような違いがあります。

- 必修にしたい教材が異なる
- 初級・中級・上級で学習順序が異なる
- 特定のレッスンだけを組み合わせたい
- 独自カリキュラムに沿って教材を公開したい
- 受講者に推奨する学習経路を別に定義したい

そこで、既存教材を再利用しながら、スクール側が独自の学習ロードマップを作成・公開できる仕組みを整備しました。

## 2. 前任者の実装を引き継いだ時点の状態

この機能は、前任者による実装の途中から引き継ぎました。

前任者が作成していたのは、主に次の範囲でした。

- ロードマップのCRUD機能の途中まで
- CMSでロードマップを新規作成する機能
- 新規作成機能を使って作成したサンプルロードマップ
- そのサンプルロードマップを学習者向けページに単純表示する処理

つまり、ロードマップを作成して表示する最小限の流れは存在していましたが、プロダクトの機能として必要な運用・学習導線・データ整合性までは完成していない状態でした。

例えば、次のような点が未整備でした。

- CRUDの一連の操作が完成していない
- 教材を柔軟に選択・解除・並び替えする管理画面が不十分
- 公開・非公開の扱いが整理されていない
- 学習者向けページがサンプル表示中心だった
- 既存コースとロードマップの進捗計算を統一する必要がある
- ロードマップから教材へ移動した後の文脈維持が不足している
- 既存プロジェクトのUI・API・設計標準からずれている部分がある

そのため、既存コードをそのまま継ぎ足すのではなく、前任者の実装意図と既存データ構造を読み解いたうえで、機能全体を現在のプロジェクト標準に合わせて再構成しました。

## 3. 引き継ぎ時に意識したこと

既存コードを確認するときは、すぐに書き換え始めるのではなく、まず次の点を整理しました。

- どの画面がロードマップに関係しているか
- ロードマップと教材の関連データはどう管理されているか
- 作成・更新・削除の責務はどこにあるか
- 学習者の進捗はどのデータから計算されるか
- 公開状態はどの層で判定されているか
- サンプル表示と本来のプロダクト仕様にどの差があるか
- 変更すると影響する既存画面やAPIはどこか

既存実装には、表面上は分かりにくくても、過去データや既存画面との互換性を保つための前提が含まれている場合があります。

そのため、次のような順番で進めました。

```text
前任者の実装範囲を把握する
  ↓
既存仕様と不足している仕様を整理する
  ↓
データの流れと既存の学習導線を追う
  ↓
プロジェクト標準とのずれを確認する
  ↓
現在の技術方針へ置き換える
  ↓
UI・API・DBを通して検証する
```

## 4. プロジェクト標準に合わせた改修

引き継いだ実装には、既存プロジェクトで標準としているUIや設計方針と異なる部分がありました。

そこで、機能を完成させるだけでなく、既存機能との一貫性を保つために、次のような修正も行いました。

- プロジェクト標準のUIコンポーネントへ置き換え
- 既存画面と揃ったフォーム・モーダル・アコーディオン構成へ変更
- ローディング、エラー、空状態の表示を統一
- API・サービス・リポジトリの責務を整理
- 既存の権限・公開状態の扱いに合わせて取得経路を修正
- キャッシュ無効化や再取得のタイミングを既存パターンに合わせて調整
- App Router、Server Component、Client Componentの役割を整理

### 技術方針の変更

既存実装を引き継いだ一方で、プロジェクトでは技術方針も変更されていました。

- API: FrourioからtRPCへ
- UI: Chakra UIからMantine UIへ
- APIクライアント: 既存方式からtRPCクライアントへ

単なるライブラリの置き換えではなく、既存仕様を維持しながら、現在のプロジェクト標準に合わせて構成を更新しました。

## 5. CMS管理画面の設計

### 5.1 ロードマップのCRUD

管理者がロードマップを作成・取得・更新・削除できるよう、CRUD機能を整理しました。

管理対象には、次のような情報があります。

- タイトル
- 説明
- 公開状態
- URL用のslug
- 選択された教材
- 教材の学習順序

作成中のロードマップは非公開にしておき、教材構成を確認してから公開できるようにしました。

```text
作成中
  ↓
教材を選択
  ↓
学習順序を調整
  ↓
内容を確認
  ↓
公開
```

### 5.2 アコーディオンによる教材選択

教材数が多い場合でも構造を把握しやすいよう、コースやレッスングループを階層的に表示しました。

```text
コース
  └ レッスングループ
      └ レッスン
          └ チュートリアル
```

コース単位やレッスングループ単位でまとめて選択できるようにし、教材を1件ずつ追加するよりも効率よくカリキュラムを構成できるようにしました。

### 5.3 選択済み教材の並び替え

選択した教材はドラッグ＆ドロップで並び替えられるようにしました。

```ts
const orderedItems = items.map((item, index) => ({
  id: item.id,
  order: index
}))

await saveOrder(orderedItems)
```

画面上の一時的な並び順と、保存後の永続化データを分けて扱い、変更後の順序をまとめてAPIへ送信する構成にしました。

### 5.4 公開・非公開の切り替え

管理者が作成途中のロードマップを非公開で保持し、内容を確認してから公開できるようにしました。

公開状態は画面上で非表示にするだけでは不十分です。学習者向けAPIの取得処理やURL直接アクセス、教材遷移でも公開状態を確認する必要があります。

## 6. 学習者向けページと進捗表示

学習者向けページでは、ロードマップの概要、含まれる教材、学習順序、完了状態、進捗を表示しました。

単なるサンプルロードマップの表示から、ログインユーザーが実際の学習経路として利用できるページへ拡張しています。

### 垂直タイムライン

進捗は垂直タイムライン形式で表示しました。

```text
● 基礎文法                 完了
│
● コンポーネント設計       完了
│
◉ API設計                  学習中
│
○ データベース             未着手
```

これにより、学習者が「どこまで完了したか」「現在どこにいるか」「次に何を学ぶか」を把握しやすくしました。

## 7. コース経由とロードマップ経由の整合性

ロードマップには、既存コースにも含まれているレッスンが登録されます。同じレッスンをコース経由で開く場合とロードマップ経由で開く場合に、進捗率や次の遷移先が異なると、学習者に不整合が見える可能性があります。

### 7.1 進捗率の算出方式を共通化

ロードマップ専用の別ロジックを作るのではなく、既存コースと同じ進捗計算処理をロードマップでも利用しました。

```ts
const achievementRatio = calculateCourseAchievement(
  roadMapLessonsWithProgress.map(({ lesson }) => lesson)
)
```

ロードマップに含まれるレッスンを、コース側と同じ算出関数へ渡すことで、コース経由とロードマップ経由で進捗率の基準がずれないようにしました。

既存ロジックを再利用することで、似た処理を別々に実装した場合に起こりやすい仕様差分や修正漏れも抑えています。

### 7.2 URLでロードマップの文脈を維持

ロードマップからレッスンやチュートリアルへ移動した後も、ロードマップの文脈を維持できるよう、URLに次のクエリパラメータを付与しました。

```text
/lessons/{lessonId}?from=roadmap&roadmapId={roadmapId}
```

```ts
const queryParams =
  from === 'roadmap' && roadmapId
    ? `?from=roadmap&roadmapId=${roadmapId}`
    : ''
```

この情報を次の画面・操作へ引き継ぐことで、次のような導線を実現しました。

- パンくずにロードマップ名を表示する
- 「レッスンに戻る」で元のロードマップへ戻る
- ロードマップ内の前後レッスンを表示する
- 次のチュートリアルやチャレンジでもロードマップ文脈を維持する
- コース全体の順序ではなく、ロードマップ独自の順序でナビゲーションする

### 7.3 ロードマップ内の前後レッスンを取得

通常のコース順をそのまま使うと、ロードマップに含まれていないレッスンへ遷移する可能性があります。

そこで、`from=roadmap` と `roadmapId` がある場合は、ロードマップ内の前後関係を取得するAPIを利用します。

```ts
const useRoadmapNav = from === 'roadmap' && !!roadmapId

const roadmapAdjacentQuery =
  trpc.roadMap.getAdjacentLessonsForNavigation.useQuery(
    { roadMapId: roadmapId ?? '', lessonId: lesson.id },
    { enabled: useRoadmapNav }
  )
```

ロードマップ用の取得に失敗した場合は通常のコースナビゲーションへ戻すフォールバックも用意し、既存導線への影響を抑えました。

この対応では、クエリパラメータを単なるURL上の情報ではなく、**どの学習経路から来たかを後続画面でも保持するためのコンテキスト情報**として扱いました。

## 8. tRPCとZodによるAPI設計

### 8.1 型安全なCRUD

tRPCを利用し、ロードマップの作成・取得・更新・削除を型安全なプロシージャとして整理しました。

```text
create
  └ 新規ロードマップを作成
getById / getBySlug
  └ ロードマップを取得
update
  └ タイトル・教材・公開状態などを更新
remove
  └ ロードマップと関連データを削除
```

APIの入力・出力型をフロントエンドとバックエンドで共有することで、画面側とサーバー側の想定がずれたまま残るリスクを減らしました。

### 8.2 Zodによる入力バリデーション

フロントエンドの入力制御だけに依存せず、サーバー側でも入力を検証しました。

```ts
const RoadmapInput = z.object({
  title: z.string().trim().min(1),
  description: z.string().optional(),
  lessonGroupIds: z.array(z.string()).default([]),
  isPublished: z.boolean()
})
```

実際のスキーマや名前はプロジェクト固有のため、ここでは一般化しています。

## 9. slug・トランザクション・関連データ

### 9.1 slugの自動生成と重複チェック

ロードマップのURLに利用するslugを自動生成し、既存slugとの重複を確認する処理を実装しました。

```ts
const baseSlug = toSlug(title)
const slug = await createUniqueSlug(baseSlug)
```

### 9.2 トランザクションによる整合性確保

ロードマップの更新では、本体だけでなく教材との関連や並び順も同時に変更されます。

```text
ロードマップ本体を更新
  ↓
既存の教材関連を整理
  ↓
新しい教材関連を保存
  ↓
並び順を保存
```

途中で失敗した場合に一部の更新だけが残らないよう、複数の更新をトランザクション内で扱いました。

### 9.3 削除時のカスケード

ロードマップ削除後に関連データだけが残ると、孤立レコードや意図しない参照の原因になります。

そのため、ロードマップと教材の関連データを含め、削除時に不要なレコードが残らないようカスケード削除を含めて設計しました。

## 10. キャッシュと表示パフォーマンス

管理画面と学習者向けページでは、必要なデータと更新頻度が異なります。

- 管理画面: 更新操作が多く、最新状態の反映が重要
- 学習者向けページ: 表示速度と進捗の最新性のバランスが重要

そのため、画面ごとにデータ取得とキャッシュの扱いを見直しました。

```text
管理者がロードマップを更新
  ↓
関連キャッシュを更新・無効化
  ↓
公開ページが古い教材構成を表示しない
```

また、教材完了後にロードマップの進捗が古いまま残らないよう、更新後の再取得やキャッシュ無効化のタイミングも調整しました。

## 11. 特に難しかったこと

### 11.1 途中まで作られた機能を完成形へ広げること

前任者の実装には、ロードマップを新規作成してサンプルを表示するための基礎がありました。一方で、プロダクトとして継続利用するには、編集・削除・公開制御・教材選択・進捗・遷移などを一つの機能としてつなぐ必要がありました。

既存コードを全面的に破棄するのではなく、利用できる部分と作り直す部分を見極めながら、機能の境界を整理しました。

### 11.2 既存標準とのずれを修正しながら開発すること

引き継いだ画面には、既存プロジェクトのUIや実装方針と異なる部分がありました。

そのため、ロードマップ固有の機能だけでなく、次のような共通体験も合わせて見直しました。

- UIコンポーネント
- フォームとバリデーション
- ローディング・エラー・空状態
- 権限や公開状態の扱い
- API・サービス・リポジトリの責務
- キャッシュと再取得の方針

### 11.3 学習経路をまたいだ状態の一貫性

同じレッスンをコースから開く場合とロードマップから開く場合で、進捗表示や「次へ」の遷移先が変わると、学習者は現在の文脈を失ってしまいます。

そのため、進捗率���計算は共通化し、ナビゲーションだけはURLの文脈に応じて切り替える構成にしました。

```text
進捗率：共通ロジックを利用
ナビゲーション：from=roadmap の場合はロードマップ順
表示文脈：roadmapId を引き継ぐ
```

## 13. まとめ

カスタム学習ロードマップ機能では、前任者が途中まで実装していたロードマップの作成・サンプル表示機能を引き継ぎ、スクール側の管理画面から学習者向けページまでを一つのプロダクト機能として再構成しました。

特に取り組んだことは次の通りです。

- 途中まで作られていたCRUDとサンプル表示の実装範囲を把握した
- 不足していた教材選択・並び替え・公開制御・進捗・遷移を追加した
- 既存プロジェクトのUI・API・設計標準とのずれを修正した
- FrourioからtRPCへ、Chakra UIからMantine UIへ移行した
- CMSと学習者向けページを一貫したデータフローで接続した
- コースとロードマップで進捗率の算出方式を統一した
- `from=roadmap` と `roadmapId` により学習経路の文脈を維持した
- ロードマップ内の前後関係に基づくナビゲーションを実装した
- Zodによるサーバー側バリデーションを整備した
- slug重複、トランザクション、カスケード削除を扱った
- キャッシュと再取得を調整し、表示の最新性を確保した

機能の実装はマージ済みで、他の関連機能と順次統合しながら、段階的に本番環境へ反映される予定です。一部のUI/UX仕様については、プロダクト全体との整合性を踏まえて継続的に改善しています。

この開発を通じて、フロントエンドの画面実装だけでなく、途中まで作られた既存機能を読み解き、プロジェクト標準へ合わせながらAPI、DB、データ整合性、キャッシュ、運用フロー、学習経路のコンテキストまで設計する経験を得ました。
