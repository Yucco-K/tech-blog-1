## はじめに

教育系Webサービスで、スクールごとに教材を組み合わせて独自の学習経路を作成できる「カスタム学習ロードマップ機能」の開発を担当しました。

この機能では、管理画面でロードマップを作成し、教材を選択・並び替え・公開します。学習者向けページでは、ロードマップに沿った教材と学習進捗を確認できます。

単なる一覧画面の追加ではなく、CMS、学習者向けUI、API、データベース、公開状態、進捗表示、キャッシュまで複数の領域にまたがる機能でした。さらに、前任者の実装を引き継ぎ、プロジェクトの技術方針変更に合わせて改修する必要もありました。

:::

## 1. なぜカスタムロードマップが必要だったのか

固定されたコース構成だけでは、スクールごとの学習方針に合わせて教材を組み替えることが難しいという課題がありました。

例えば、スクールによって次のような違いがあります。

- 必修にしたい教材が異なる
- 初級・中級・上級で学習順序が異なる
- 特定のレッスンだけを組み合わせたい
- 独自カリキュラムに沿って教材を公開したい
- 受講者に推奨する学習経路を別に定義したい

そこで、既存教材を再利用しながら、スクール側が独自の学習ロードマップを作成・公開できる仕組みを実装しました。

## 2. 機能全体の構成

大きく分けると、次の2つの画面とAPI・データ層で構成されています。

```text
CMS管理画面
  ├─ ロードマップ作成・編集・削除
  ├─ 教材の選択・解除
  ├─ 教材の並び替え
  └─ 公開・非公開の切り替え

API / データ層
  ├─ CRUD
  ├─ 入力バリデーション
  ├─ slug生成・重複チェック
  ├─ 関連教材の更新
  └─ トランザクション

学習者向けページ
  ├─ ロードマップ概要
  ├─ 学習順序
  ├─ 完了状態
  └─ 進捗タイムライン
```

管理者が作ったロードマップを学習者が閲覧するだけでなく、教材の構成と進捗表示が同じデータをもとに一貫して動くことを重視しました。

## 3. 既存実装を引き継ぐときに意識したこと

この機能は、前任者による既存実装を引き継いで開発しました。

既存コードを見たときに、すぐ書き換え始めるのではなく、まず次の点を確認しました。

- どの画面がロードマップに関係しているか
- ロードマップと教材の関連データはどう管理されているか
- 作成・更新・削除の境界はどこか
- 学習者の進捗はどのデータから計算されるか
- 公開状態はどの層で判定されているか
- 既存実装が前提としている仕様は何か
- 変更すると影響する画面やAPIはどこか

既存実装には、表面上は分かりにくくても、既存画面との互換性や過去データとの整合性を保つための処理が含まれている場合があります。

そのため、単純な置き換えではなく、

```text
既存仕様を理解する
  ↓
データの流れを追う
  ↓
現在の技術方針に置き換える
  ↓
既存画面との互換性を確認する
  ↓
UI・API・DBを通して検証する
```

という順番で進めました。

## 4. 技術方針の変更に合わせた改修

既存実装を引き継いだ一方で、プロジェクトの技術方針が変わっていました。

今回の主な移行は次の2つです。

- API: FrourioからtRPCへ
- UI: Chakra UIからMantine UIへ

### APIをtRPCへ移行

tRPCを利用することで、APIの入力・出力型をフロントエンドとバックエンドで共有できます。

例えば、ロードマップ作成APIを次のように考えます。

```ts
const input = {
  title: 'フロントエンド基礎',
  description: '基礎から段階的に学ぶロードマップ',
  selectedLessonGroupIds: ['group-a', 'group-b'],
  isPublished: false
}
```

APIの入力項目を変更したとき、呼び出し側の型にも影響が伝わるため、画面側とサーバー側の想定がずれたまま残るリスクを減らせます。

### UIをMantine UIへ移行

UIライブラリの移行では、コンポーネントを置き換えるだけでなく、次の点も確認しました。

- フォームのバリデーション表示
- モーダルやアコーディオンの挙動
- レスポンシブ対応
- ボタンのdisabled・loading状態
- 選択状態の表示
- エラー・空状態の表示

既存仕様を保ちつつ、プロジェクト内の現在のUIパターンに揃えることを意識しました。

## 5. CMS管理画面の設計

### 5.1 ロードマップのCRUD

管理者がロードマップを作成・編集・削除できるようにしました。

管理対象には、次のような情報があります。

- タイトル
- 説明
- 公開状態
- URL用のslug
- 選択された教材
- 教材の学習順序

作成中のロードマップは非公開にしておき、内容を確認してから公開できます。

```text
作成中
  ↓
教材を選択
  ↓
学習順序を調整
  ↓
内容を確認
  ↓
公開
```

この流れにより、編集途中の状態が学習者へそのまま表示されることを防ぎます。

### 5.2 アコーディオンによる教材選択

教材数が多い場合でも構造を把握しやすいよう、コースやレッスングループを階層的に表示しました。

```text
コース
  └ レッスングループ
      └ レッスン
          └ チュートリアル
```

また、コース単位でまとめて選択できるようにしました。教材を1件ずつ追加するよりも、カリキュラム全体を組み立てやすくなります。

### 5.3 選択済み教材の並び替え

選択した教材は、ドラッグ＆ドロップで学習順序を変更できるようにしました。

画面上での順番変更だけでなく、保存時には最終的な順序をまとめてAPIへ送信します。

```ts
const orderedItems = items.map((item, index) => ({
  id: item.id,
  order: index
}))

await saveOrder(orderedItems)
```

順序変更のUIと保存処理を分けて考えることで、画面上の一時状態と永続化された状態を整理しました。

### 5.4 公開・非公開の切り替え

作成途中のロードマップを公開しないため、公開状態を管理画面から切り替えられるようにしました。

公開状態は画面の表示だけでなく、学習者向けデータ取得時にも確認する必要があります。フロントエンドで非表示にするだけでは、APIやURL直接アクセスから閲覧できる可能性が残るためです。

## 6. 学習者向けページと進捗表示

学習者向けページでは、ロードマップの概要と含まれる教材を学習順に表示しました。

単なる教材一覧ではなく、学習者が次の行動を理解できることを重視しています。

- どのロードマップを学んでいるか
- どこまで完了したか
- 現在どの教材にいるか
- 次に何を学ぶか
- 未完了の教材がどこにあるか

### 垂直タイムライン

進捗は垂直タイムライン形式で表示しました。

```text
● 基礎文法                 完了
│
● コンポーネント設計       完了
│
◉ API設計                  学習中
│
○ データベース             未着手
```

この形式により、ロードマップが単なるリストではなく、学習経路として理解しやすくなります。

進捗表示では、完了状態の取得タイミングやキャッシュも関係します。教材を完了した直後に古い状態が残らないよう、更新後の再取得やキャッシュの扱いも調整しました。

## 7. tRPCとZodによるAPI設計

### 7.1 入力バリデーション

ロードマップ作成・更新では、フロントエンドの入力制御だけに依存せず、サーバー側でも入力を検証しました。

対象となる値の例です。

- タイトルが空でないか
- slugが許可された形式か
- 教材IDが有効か
- 同じ教材が重複していないか
- 並び順が不正な値になっていないか
- 公開状態が許可された値か

```ts
const RoadmapInput = z.object({
  title: z.string().trim().min(1),
  description: z.string().optional(),
  lessonGroupIds: z.array(z.string()).default([]),
  isPublished: z.boolean()
})
```

実際のスキーマや名前はプロジェクト固有のため、ここでは一般化しています。

### 7.2 型安全なCRUD

ロードマップの作成・取得・更新・削除をtRPCのプロシージャとして整理しました。

```text
create
  └ 新規ロードマップを作成
getBySlug
  └ 学習者向けに公開ロードマップを取得
update
  └ タイトル・教材・公開状態などを更新
remove
  └ ロードマップと関連データを削除
```

入力型とレスポンス型が共有されるため、画面側で存在しないフィールドを参照したり、必須項目を渡し忘れたりする問題を見つけやすくなります。

## 8. slugの自動生成と重複チェック

ロードマップをURLで参照しやすくするため、slugを利用しました。

タイトルなどからslugを生成する場合、同じタイトルのロードマップが複数作られる可能性があります。そのため、保存前に既存slugとの重複を確認しました。

```ts
const baseSlug = toSlug(title)
const slug = await createUniqueSlug(baseSlug)
```

重要なのは、フロントエンドで「空いているように見える」と判断するだけでは不十分な点です。同時に複数の作成処理が走る可能性もあるため、サーバー側の一意制約や保存時のエラーも考慮する必要があります。

## 9. トランザクションと関連データの整合性

ロードマップの更新や削除では、ロードマップ本体だけでなく、教材との関連データも変更されます。

例えば、教材の選択を更新する場合は次のような処理が発生します。

```text
ロードマップ本体を更新
  ↓
既存の教材関連を整理
  ↓
新しい教材関連を保存
  ↓
並び順を保存
```

途中で失敗すると、ロードマップ本体だけ更新され、教材構成が古いままになる可能性があります。

そこで、複数の更新をトランザクション内で扱い、全体が成功するか、全体を元に戻すかのどちらかになるようにしました。

### 削除時のカスケード

ロードマップを削除したあとに、関連する中間データだけが残ると、孤立レコードや意図しない参照の原因になります。

そのため、削除時に関連データをどう扱うかを整理し、不要な関連レコードが残らないようカスケード削除を含めて設計しました。

```text
ロードマップ削除
  ├─ 教材との関連を削除
  ├─ 並び順情報を削除
  └─ 不要な参照を残さない
```

削除処理は「画面から消えたか」だけでなく、データベースに不要な情報が残っていないかまで確認する必要があります。

## 10. キャッシュと表示パフォーマンス

管理画面と学習者向けページでは、必要なデータと更新頻度が異なります。

- 管理画面: 更新操作が多く、最新状態の反映が重要
- 学習者向けページ: 表示速度と進捗の最新性のバランスが重要

そのため、画面ごとにデータ取得とキャッシュの扱いを見直しました。

```text
管理者がロードマップを更新
  ↓
関連キャッシュを更新・無効化
  ↓
公開ページが古い教材構成を表示しない
```

キャッシュは有効にすればよいわけではなく、どのデータをどの期間保持し、どの操作で更新するかを決める必要があります。

## 11. 特に難しかったこと

### 11.1 既存仕様と新しい技術方針の両立

既存実装を新しいライブラリへ置き換えるとき、見た目やコードの書き方だけを変えても、既存仕様が壊れる可能性があります。

前任者のコードから、次のような「暗黙の仕様」を読み取る必要がありました。

- どの教材を選べるのか
- 公開状態はどの画面で制御するのか
- 削除時に何を残すのか
- 進捗をどの単位で計算するのか
- 更新後にどのデータを再取得するのか

### 11.2 関連データを含む更新・削除

ロードマップ単体の更新なら比較的単純ですが、教材との関連、順序、公開状態、進捗が加わると、処理の境界が複雑になります。

「画面で正しく見える」だけでなく、保存に失敗した場合や削除した場合も含めて設計する必要がありました。

### 11.3 学習者向けの理解しやすさ

管理者が設定できる情報量が増えるほど、学習者向け画面は複雑になりやすくなります。

そのため、管理画面では柔軟性を確保しつつ、学習者向けページでは、現在地と次の行動が分かることを優先しました。

## 13. まとめ

カスタム学習ロードマップ機能では、管理者が教材を組み合わせて独自の学習経路を作成し、学習者がその経路に沿って学習・進捗確認できるところまでを一貫して開発しました。

特に取り組んだことは次の通りです。

- 既存実装を引き継ぎ、仕様とデータの流れを理解した
- FrourioからtRPCへ、Chakra UIからMantine UIへ移行した
- CMSで教材の選択・並び替え・公開制御を実装した
- 学習者向けに進捗タイムラインを実装した
- Zodによるサーバー側バリデーションを整備した
- slug重複、トランザクション、カスケード削除を扱った
- キャッシュと再取得を調整し、表示の最新性を確保した

機能はマージ済みで、本番環境に反映されています。一部のUI/UX仕様については、プロダクト全体との整合性を踏まえて継続的に改善しています。

この開発を通じて、フロントエンドの画面実装だけでなく、API、DB、データ整合性、キャッシュ、運用フローまでを一つのプロダクト機能として設計する経験を得ました。
