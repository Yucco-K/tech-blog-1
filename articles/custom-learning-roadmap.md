## はじめに

教育系Webサービスで、スクールごとに教材を組み合わせて独自の学習経路を作成できる「カスタム学習ロードマップ機能」の開発を担当しました。

管理画面でロードマップを作成・編集し、教材を選択・並び替え・公開します。学習者向けページでは、ロードマップに沿った教材、学習順序、進捗を確認できます。

この機能は、CMS、学習者向けUI、API、データベース、公開状態、進捗計算、既存の学習導線まで複数の領域にまたがっていました。また、前任者が途中まで実装していた機能を引き継ぎ、プロジェクト標準に合わせて再構成する必要もありました。

:::message
この記事では、守秘義務に配慮してプロジェクト名、内部URL、Issue・PR番号、具体的なモデル名や変数名を一般化しています。コードは実務コードそのものではなく、考え方を説明するためのサンプルです。
:::

## 1. なぜカスタムロードマップが必要だったのか

固定されたコース構成だけでは、スクールごとの学習方針に合わせて教材を組み替えることが難しいという課題がありました。

例えば、スクールによって次のような違いがあります。

- 必修にしたい教材が異なる
- 初級・中級・上級で学習順序が異なる
- 特定のレッスンだけを組み合わせたい
- 独自カリキュラムに沿って教材を公開したい
- 受講者に推奨する学習経路を別に定義したい

そこで、既存教材を再利用しながら、スクール側が独自の学習ロードマップを作成・公開できる仕組みを整備しました。

## 2. 途中まで作られた実装の引き継ぎ

前任者が実装していたのは、ロードマップのCRUD機能の一部、新規作成画面、作成したサンプルロードマップを学習者向けページに表示する処理まででした。

ロードマップを作成して表示する最小限の流れは存在していましたが、プロダクトとして運用するには、次の機能が必要でした。

- CRUDの完成
- 教材の選択・解除・並び替え
- 公開・非公開制御
- 実際のユーザー向け進捗表示
- ロードマップ内の学習ナビゲーション
- 既存コースとの進捗計算の整合性
- UI・API・設計のプロジェクト標準への統一

既存コードをそのまま継ぎ足すのではなく、前任者の実装意図、既存データ構造、既存の学習導線を確認したうえで、利用できる部分と作り直す部分を整理しました。

```text
前任者の実装範囲を把握する
  ↓
既存仕様と不足仕様を整理する
  ↓
データの流れと学習導線を追う
  ↓
プロジェクト標準との差分を確認する
  ↓
機能を実装・再構成する
  ↓
UI・API・DBを通して検証する
```

## 3. プロジェクト標準への適合

引き継いだ実装には、既存プロジェクトで標準としているUIや設計方針と異なる部分がありました。機能を動かすだけでなく、既存機能との一貫性を保つため、以下も合わせて修正しました。

- UIコンポーネント、フォーム、モーダル、アコーディオンの統一
- ローディング・エラー・空状態の表示統一
- API・サービス・リポジトリの責務整理
- 権限・公開状態を考慮した取得経路の整理
- キャッシュ無効化と再取得タイミングの調整
- App Router、Server Component、Client Componentの役割整理

さらに、プロジェクトの技術方針変更に合わせて、APIをFrourioからtRPCへ、UIをChakra UIからMantine UIへ移行しました。

単なるライブラリの置き換えではなく、既存仕様を維持しながら、現在のプロジェクト標準へ構成を合わせることを意識しました。

## 4. CMS管理画面

### 4.1 ロードマップのCRUDと公開制御

管理者がロードマップを作成・取得・更新・削除できるようにしました。

管理対象には次の情報があります。

- タイトル
- 説明
- 公開状態
- URL用のslug
- 選択された教材
- 教材の学習順序

作成中のロードマップは非公開で保持し、教材構成を確認してから公開できます。

```text
作成中
  ↓
教材を選択
  ↓
学習順序を調整
  ↓
内容を確認
  ↓
公開
```

公開状態は画面で非表示にするだけでは不十分です。学習者向けAPIの取得処理、URL直接アクセス、教材遷移でも公開状態を確認するようにしました。

### 4.2 階層的な教材選択

教材数が多い場合でも構造を把握しやすいよう、コースやレッスングループを階層的に表示しました。

```text
コース
  └ レッスングループ
      └ レッスン
          └ チュートリアル
```

コース単位やレッスングループ単位でまとめて選択できるため、教材を1件ずつ追加するよりも効率よくカリキュラムを構成できます。

### 4.3 選択済み教材の並び替え

選択した教材は、ドラッグ＆ドロップで並び替えられるようにしました。画面上の一時的な順序と保存済みの順序を分けて管理し、保存時に最終的な順序をまとめてAPIへ送信します。

```ts
const orderedItems = items.map((item, index) => ({
  id: item.id,
  order: index
}))

await saveOrder(orderedItems)
```

## 5. 学習者向けページと進捗表示

学習者向けページでは、サンプルロードマップを単純に表示する状態から、ログインユーザーが実際の学習経路として利用できるページへ拡張しました。

ロードマップの概要、含まれる教材、学習順序、完了状態、進捗を表示し、進捗は垂直タイムラインで可視化しました。

```text
● 基礎文法                 完了
│
● コンポーネント設計       完了
│
◉ API設計                  学習中
│
○ データベース             未着手
```

学習者が「どこまで完了したか」「現在どこにいるか」「次に何を学ぶか」を把握しやすい構成を目指しました。

## 6. コース経由とロードマップ経由の整合性

同じレッスンをコース経由とロードマップ経由で開く場合に、進捗率や次の遷移先が異なると、学習者に不整合が見えてしまいます。そこで、進捗計算とナビゲーションを分けて設計しました。

### 6.1 進捗率の算出方式を共通化

ロードマップ専用の別ロジックを作るのではなく、既存コースと同じ進捗計算処理を利用しました。

```ts
const achievementRatio = calculateCourseAchievement(
  roadMapLessonsWithProgress.map(({ lesson }) => lesson)
)
```

ロードマップのレッスンをコース側と同じ算出関数へ渡すことで、学習経路によって進捗率の基準がずれないようにしました。共通ロジックの再利用により、仕様差分や修正漏れも抑えています。

### 6.2 URLでロードマップの文脈を維持

ロードマップからレッスンやチュートリアルへ移動した後も、元の学習経路を維持できるよう、URLにクエリパラメータを付与しました。

```text
/lessons/{lessonId}?from=roadmap&roadmapId={roadmapId}
```

```ts
const queryParams =
  from === 'roadmap' && roadmapId
    ? `?from=roadmap&roadmapId=${roadmapId}`
    : ''
```

この情報を次の画面・操作へ引き継ぐことで、次の導線を実現しました。

- パンくずにロードマップ名を表示する
- 「レッスンに戻る」で元のロードマップへ戻る
- ロードマップ内の前後レッスンを表示する
- 次のチュートリアルやチャレンジでも文脈を維持する
- コース全体ではなく、ロードマップ独自の順序で移動する

### 6.3 ロードマップ内の前後レッスン

`from=roadmap` と `roadmapId` がある場合は、ロードマップ内の前後関係を取得するAPIを利用します。通常のコース順を使って、ロードマップに含まれていないレッスンへ遷移することを防ぐためです。

```ts
const useRoadmapNav = from === 'roadmap' && !!roadmapId

const roadmapAdjacentQuery =
  trpc.roadMap.getAdjacentLessonsForNavigation.useQuery(
    { roadMapId: roadmapId ?? '', lessonId: lesson.id },
    { enabled: useRoadmapNav }
  )
```

ロードマップ用の取得に失敗した場合は、通常のコースナビゲーションへ戻すフォールバックも用意しました。

## 7. tRPCとZodによるAPI設計

### 7.1 型安全なCRUD

tRPCを利用し、ロードマップの作成・取得・更新・削除を型安全なプロシージャとして整理しました。

```text
create       └ 新規ロードマップを作成
getById      └ 管理画面向けに取得
getBySlug    └ 公開ページ向けに取得
update       └ タイトル・教材・公開状態などを更新
remove       └ ロードマップと関連データを削除
```

APIの入力・出力型をフロントエンドとバックエンドで共有することで、両者の想定がずれたまま残るリスクを減らしました。

### 7.2 Zodによる入力バリデーション

フロントエンドだけでなく、サーバー側でも入力を検証しました。

```ts
const RoadmapInput = z.object({
  title: z.string().trim().min(1),
  description: z.string().optional(),
  lessonGroupIds: z.array(z.string()).default([]),
  isPublished: z.boolean()
})
```

実際のスキーマや名前はプロジェクト固有のため、ここでは一般化しています。

## 8. slug・トランザクション・関連データ

### 8.1 slugの自動生成と重複チェック

ロードマップのURLに利用するslugを自動生成し、既存slugとの重複を確認しました。

```ts
const baseSlug = toSlug(title)
const slug = await createUniqueSlug(baseSlug)
```

### 8.2 トランザクションによる整合性確保

ロードマップの更新では、本体だけでなく教材との関連や並び順も変更されます。

```text
ロードマップ本体を更新
  ↓
既存の教材関連を整理
  ↓
新しい教材関連を保存
  ↓
並び順を保存
```

途中で失敗した場合に一部の更新だけが残らないよう、複数の更新をトランザクション内で扱いました。

### 8.3 削除時のカスケード

ロードマップ削除後に関連データだけが残らないよう、教材との関連データを含めた削除方針を整理し、カスケード削除を設計しました。

## 9. キャッシュと表示パフォーマンス

管理画面は更新操作の反映速度、学習者向けページは表示速度と進捗の最新性が重要です。そのため、画面ごとにデータ取得とキャッシュの扱いを見直しました。

```text
管理者がロードマップを更新
  ↓
関連キャッシュを更新・無効化
  ↓
公開ページが古い教材構成を表示しない
```

教材完了後にもロードマップの進捗が古いまま残らないよう、再取得やキャッシュ無効化のタイミングを調整しました。

## 10. テスト工程

この機能は、CMSの操作、公開範囲、進捗計算、既存コースとの整合性、学習者向けの遷移が連動するため、実装箇所ごとに確認するのではなく、データ生成から画面遷移までを段階的に検証しました。

### 10.1 スキーマ・型・静的な確認

まず、入力値とデータの受け渡しに問題がないことを確認しました。

- `RoadmapUpsertSchema` による作成・更新入力の検証
- `RoadmapDeleteSchema` による削除IDの検証
- タイトル、説明、レッスングループ選択数の必須チェック
- 公開状態の真偽値チェック
- tRPCルーターの入力・出力型の確認
- フロントエンドとバックエンド間での型の不一致確認
- 不要な型アサーションや未使用の型・importの整理
- App Router、Server Component、Client Componentの境界確認

特に、ロードマップの作成・更新・削除を別々のAPIとして追加するのではなく、入力スキーマとtRPCの型を通して一貫して扱えることを確認しました。

### 10.2 API・権限の確認

次に、各APIが想定したユーザーだけから呼び出せることを確認しました。

#### CMS向けAPI

- ロードマップ一覧取得
- 非公開ロードマップを含むCMS一覧取得
- ロードマップ詳細取得
- ロードマップ作成
- ロードマップ更新
- ロードマップ削除

#### 学習者向けAPI

- 公開ロードマップ一覧取得
- 進捗付きロードマップ取得
- パンくず表示用のロードマップ情報取得
- ロードマップ内の前後レッスン取得

確認した主なケースは次の通りです。

- CMSユーザーは非公開ロードマップを確認・編集できる
- 一般ユーザーには非公開ロードマップが返らない
- 公開ロードマップだけが学習者向け一覧に表示される
- 非公開のレッスングループ・レッスン・チャレンジが一般ユーザーに混入しない
- ロードマップIDを変更した不正なリクエストで、別ロードマップの情報を取得できない
- 存在しないIDを指定した場合に適切なエラーになる

画面で非表示になっているだけではなく、サーバー側の取得処理でも公開状態と権限が制御されていることを確認しました。

### 10.3 CMS画面の手動確認

CMSでは、作成から削除までの一連の操作を実際に確認しました。

1. `/cms/roadmaps`を開く
2. 「新規ロードマップ作成」を押す
3. タイトルと説明を入力する
4. コースをアコーディオンで開く
5. レッスングループを個別に選択する
6. コース単位で一括選択する
7. 一部だけ解除し、選択状態とindeterminate状態を確認する
8. 「すべてクリア」で選択を解除する
9. 公開スイッチをOFFのまま作成する
10. 作成したロードマップがCMS一覧に表示されることを確認する
11. 作成したロードマップを編集する
12. タイトル、説明、教材構成、公開状態を変更する
13. 保存後に一覧へ戻り、変更が反映されることを確認する
14. ロードマップを公開し、公開状態の表示が切り替わることを確認する
15. 削除確認モーダルを開き、キャンセルできることを確認する
16. 削除を実行し、一覧から消えることを確認する

入力エラーについても確認しました。

- タイトル未入力
- 説明未入力
- レッスングループ未選択
- 最大文字数を超えた入力
- 公開・非公開切り替え時の表示
- API失敗時のエラー通知
- 保存中のボタンloading状態

### 10.4 並び替えと保存状態の確認

選択済み教材の並び替えでは、画面上の状態とデータベース保存後の状態が一致することを確認しました。

- 同一コース内での並び替え
- 複数コースをまたいだ並び替え
- 並び替え後の保存
- 保存後の再取得
- 編集画面を閉じて再度開いた場合の順序維持
- 並び替えを元に戻す操作
- 選択・解除と並び替えを組み合わせた場合の状態
- 変更前の順序が誤って上書きされないこと

また、関連レコードの更新途中で失敗した場合に、ロードマップ本体だけ、または教材関連だけが更新された状態にならないことを、トランザクション設計と実データ確認の両面から確認しました。

### 10.5 学習者向けページの確認

学習者向けページでは、公開状態と進捗の組み合わせを確認しました。

- 公開ロードマップ一覧が表示される
- 公開ロードマップの詳細を開ける
- ロードマップ内のコース・レッスングループ・レッスンが順序どおりに表示される
- 非公開の教材が一般ユーザーの画面に表示されない
- レッスングループがアコーディオンで開閉できる
- 進捗リングが表示される
- 完了済み、学習中、未着手の状態が期待どおりに表示される
- 進行中のグループが初期状態で開く
- すべて完了している場合に先頭グループが開く
- 進捗データ取得に失敗しても、基本情報を表示できる
- ローディング中にスケルトンが表示される

### 10.6 コース経由とロードマップ経由の確認

同じレッスンを、コースページとロードマップページの両方から開いて比較しました。

- 同じ学習結果をもとに進捗率が算出される
- コース経由とロードマップ経由で進捗率の基準がずれない
- ロードマップ経由のURLに`from=roadmap`と`roadmapId`が付与される
- レッスンからロードマップへ戻れる
- パンくずにロードマップ名が表示される
- レッスン、チュートリアル、チャレンジへの遷移でクエリが維持される
- 完了後の「次へ」遷移でもロードマップの文脈が残る
- ロードマップ内の前後レッスンへ移動できる
- ロードマップに含まれないコース上のレッスンへ誤遷移しない
- ロードマップナビゲーションの取得失敗時に、コース側へフォールバックする

### 10.7 進捗更新とキャッシュの確認

教材を完了した直後に、各画面の進捗が古いまま残らないことを確認しました。

対象にした操作は次の通りです。

- チャレンジ完了
- クイズ回答
- スキルコーディング完了
- チュートリアル完了
- チャレンジの不正解・再挑戦
- タイムアウトやギブアップなどの状態更新

確認した画面は次の通りです。

- レッスン詳細ページ
- コース詳細ページ
- ロードマップ詳細ページ
- チャレンジ画面のパンくず
- 学習者向け進捗表示

完了処理のあとに、レッスン、コース、ロードマップの関連キャッシュが適切に再取得または無効化され、画面を再読み込みしなくても最新状態へ更新されることを確認しました。

### 10.8 データ整合性と削除の確認

最後に、更新・削除処理後のデータ状態を確認しました。

- 作成したロードマップに選択教材が正しく紐づく
- 教材の順序が保存される
- 更新後に古い関連データが残らない
- 選択解除した教材がロードマップに残らない
- ロードマップ削除後に関連レコードが残らない
- 外部キー制約に抵触しない順序で削除される
- 更新途中・削除途中の失敗で中途半端な状態にならない
- slugが重複しない
- 同じタイトルのロードマップを作成・更新できない
- 既存のコースやレッスンの進捗データに影響しない

進捗計算については、既存の達成率計算テストにロードマップ経由でも必要になるチャレンジ結果の状態や、クイズ・スキルコーディングの正解状態を反映したケースを追加して確認しました。

### 10.9 コードレビューでの確認と修正

実装後はコードレビューも行い、指摘を反映しました。主な確認・修正内容は次の通りです。

- slug生成の再帰処理をループへ変更し、衝突が続いた場合のスタック増加を防止
- ID生成をプロジェクト標準のUUID方式へ統一
- slug生成の試行回数に関するコメントと実装条件を整理
- 作成・更新・削除をトランザクションで扱う
- `imageUrl`の入力を任意値として扱う
- 不要な型定義・import・`useEffect`を削除
- 型アサーションを簡素化
- 削除確認を標準UIのモーダルで実装

- 非公開コンテンツの取得条件を確認
- 進捗計算に必要な最新のチャレンジ結果を参照するよう確認

一部の既存プロジェクト全体に関わる事項は、今回の機能のスコープ外として、TODOまたは別課題に整理しました。例えば、既存の生成ファイル管理方針などは、ロードマップ機能だけで変更すると影響範囲が大きいため、別途扱う判断にしています。

## 12. まとめ

前任者が途中まで実装していたロードマップの作成・サンプル表示機能を引き継ぎ、スクール側の管理画面から学習者向けページまでを一つのプロダクト機能として再構成しました。

主な取り組みは次の通りです。

- 不足していた教材選択・並び替え・公開制御・進捗・遷移を追加
- 既存プロジェクトのUI・API・設計標準とのずれを修正
- FrourioからtRPCへ、Chakra UIからMantine UIへ移行
- コースとロードマップで進捗率の算出方式を統一
- `from=roadmap` と `roadmapId` で学習経路の文脈を維持
- ロードマップ内の前後関係に基づくナビゲーションを実装
- Zod、slug重複チェック、トランザクション、カスケード削除を整備
- CMS操作、権限、公開範囲、画面遷移、進捗更新、キャッシュ、データ整合性を段階的に検証

機能の実装はマージ済みで、他の関連機能と順次統合しながら、段階的に本番環境へ反映される予定です。一部のUI/UX仕様については、プロダクト全体との整合性を踏まえて継続的に改善しています。

この開発を通じて、途中まで作られた既存機能を読み解き、プロジェクト標準へ合わせながら、フロントエンド、API、DB、データ整合性、キャッシュ、学習導線、そしてテスト工程までを一貫して設計する経験を得ました。
